## 一、业界调研:别人怎么做这个功能

### 1. mem0 — 开源 AI 记忆层(arXiv:2504.19413)

- **机制**:两阶段管线。①Extraction:LLM 从最新交互中提取显著事实;②Update:提取结果与既有记忆做相似度检索比对,由 LLM 决策每条记忆 **ADD / UPDATE / DELETE / NOOP**。新版转向单遍 ADD-only(提速降本)。
- **可借鉴**:「提取-归并」分两步;**NOOP 为默认**(大多数交互不改变档案)→ 我们用"出现 ≥2 次才入档"实现同一思想,防偶发污染。
- **不借鉴**:LLM 提取(每事件多一次网络调用,无声助理变卡顿助理);向量检索(localStorage 无向量库,KB 级档案全文匹配足够)。**关键差异:mem0 要从自由对话里"理解"事实,而秒策的事件源(表单字段、prev→md 对照)本身已半结构化,确定性规则够用。**

### 2. Zep / Graphiti — 时间知识图谱(arXiv:2501.13956)

- **机制**:每个事实携带有效期(t_valid / t_invalid),知道"什么现在为真、什么曾经为真、何时改变";双时间建模 + 增量更新,长期记忆检索基准上胜过 MemGPT。
- **可借鉴**:**时间衰减**——组织会变(预算档位、常用场地),每条画像条目记 firstSeen/lastSeen,注入时旧信号降权(权重 ∝ count × 0.5^(age/180天))。
- **不借鉴**:图数据库、双时间建模——单机单用户用不上,过度设计。

### 3. ChatGPT Memory — 产品形态标杆

- **机制**:两条通路。①Saved Memories:可编辑的显式事实列表(自动捕获+手动添加);②Reference Chat History:检索全部历史对话作为上下文。均可在设置中开关、查看、逐条删除。
- **可借鉴**:**用户可见、可删是一切记忆功能的信任基础**;自动捕获 + 显式管理并存的形态。P3「企业档案」卡片 = saved memories 的本地版。
- **不借鉴**:reference chat history 式"全历史塞上下文"(token 成本高;秒策历史方案本就在 localStorage,无需第二套机制)。已知问题**记忆污染**(错误事实越用越偏)是我们的前车之鉴,防线见下文注入层。

### 4. 隐式反馈研究(编辑即反馈)

- IFllm 数据集(arXiv:2606.20482):用户隐式反馈可量化用于 LLM 对齐;ScienceDirect(Njuguna 2025):**用户对 AI 建议的编辑本身就是高质量隐式反馈**;Prototypical Human-AI Collaboration Behaviors(arXiv:2505.16023):偏好学习应做 session 级优化;OpenAI 实践:显式+隐式反馈汇入共享数据层。
- **可借鉴**:秒策的独有优势——编辑器 `secObj.prev` 机制天然保存"AI 输出版本",`md` 是用户编辑后版本,**prev→md 就是免费的改写前后样本对**(正是这些研究要专门收集的数据),E2 埋点近乎零成本;P2 的 👍/👎 显式反馈权重高于被动信号(显隐混合是共识做法)。
- **不借鉴**:RLHF / reward model(需要训练基础设施,纯前端不可能)。

### 5. Grammarly tone — 克制的个性化先例

- **机制**:规则+ML 混合分析用词/句式/标点;从用户写作模式与接受/拒绝建议的历史个性化建议相关性;150 字符门槛;**不做"个人声音训练"**,只调建议相关性。
- **可借鉴**:**克制的度**——档案只影响风格词、默认值、生成侧重点,绝不试图复刻用户文风;信号统计可用确定性规则(段均长、列表占比、被删句式词表)替代 transformer。
- **不借鉴**:模型分类器(重,且引入不可解释性)。

### 取舍总表

| 来源 | 借 | 不借(理由) |
| --- | --- | --- |
| mem0 | 提取-归并两步;NOOP 默认(≥2 次入档) | LLM 提取、向量库(事件已结构化;无后端) |
| Zep | 条目级时间戳 + 衰减 | 图谱、双时间建模(过度设计) |
| ChatGPT | 记忆可见可删的形态;污染教训 | 全历史入上下文(token 成本) |
| 隐式反馈研究 | prev→md 样本对;显隐混合 | RLHF(不可能) |
| Grammarly | 个性化的克制度 | ML 分类器(不可解释) |

## 二、架构:三层纯函数 + 事件溯源

```
┌─ 捕获层(5 个埋点,全部在已有代码路径上,各加一行)─────────────────┐
│ E1 plan_generated  app.finishGen     公司事实/预算档位/人群构成      │
│ E2 section_edited  doceditor.saveNow 文风样本对(prev→md 新旧对照)   │
│ E3 section_ai_op   doceditor.runAI   热区信号(哪类章节被重写/撤销)  │
│ E4 selection_op    doceditor.runSelOp 选区级改写前后对              │
│ E5 form_defaults   app.saveDraftDebounced 表单默认值分布            │
└───────────────┬────────────────────────────────────────┘
                ↓  EP.profile.update(profile, event) → profile   纯函数,node 可测
┌─ 档案层 localStorage 键 ep_profile(单一 JSON)─────────────────────┐
│ ① facts     公司事实:名称/行业用词/场地偏好/预算档位               │
│ ② style     文风偏好:段均长/列表↔段落转换率/被删套话句式/保留术语  │
│ ③ hotspots  热区:最常被重写的章节类型 → 该类生成更谨慎             │
│ ④ defaults  表单默认值分布(venue/audience/duration/budget)        │
│ 每条目 { value, count, firstSeen, lastSeen } ← Zep 式衰减原料      │
│ 另存原始事件环形缓冲(最近 500 条)← 可解释、可重放、算法可升级     │
└───────────────┬────────────────────────────────────────┘
                ↓  EP.profile.summarize(profile, kind) → string   纯函数,≤200 字
┌─ 注入层(ai.js 3 处,零 UI 改动)───────────────────────────────────┐
│ generatePlan            → "企业档案(仅供参考,与本次活动信息冲突时  │
│                            以活动信息为准):…"                     │
│ regenSection/polish/expand → "用户偏好摘要:…"                     │
└────────────────────────────────────────────────┘
```

### 数据结构(示意)

```js
ep_profile = {
  ver: 1,
  facts: {                    // E1
    companies:  [{ value: '星海科技', count: 5, firstSeen: 0, lastSeen: 0 }],
    venues:     [{ value: '临湖山庄', count: 3, ... }],
    budgetTier: [{ value: '3万-5万',  count: 2, ... }],
    audiences:  [{ value: 'staff',    count: 4, ... }]
  },
  style: {                    // E2/E4:确定性统计,不下结论
    avgParaDelta: -0.18,      // 用户编辑后段落平均变短 → 偏简洁
    listifyRate:  0.35,        // 段落被改为列表的比率
    removedPhrases: [{ value: '综上所述', count: 4, ... }],   // 被删句式
    keptTerms:    [{ value: '赋能', count: 2, ... }]          // 保留的公司术语
  },
  hotspots: {                 // E3
    byTitle: [{ value: '预算明细', regen: 3, undoAi: 2, ... }] // 重写+撤销 → 生成需更保守
  },
  defaults: {                 // E5
    duration: [{ value: 'half', count: 6, ... }]
  },
  events: [ /* 环形缓冲,最近 500 条原始事件,供 P3 展示与重放 */ ]
}
```

## 三、关键决策与理由

### D1 事件溯源(update 纯函数),而非直接改档案字段

**为什么**:①可测试——node 断言"事件进→档案变",不依赖浏览器;②可解释——P3 设置页能人话展示"学到了 X,因为见过 N 次"(ChatGPT 式透明);③可清除——清档案=删一个键,数据与派生物分离;④可升级——将来改归并算法,重放 events 即可,不丢原始观察。

### D2 update 用确定性规则,不上 LLM(mem0 的核心差异)

**为什么**:①秒策事件源已半结构化(表单字段、md 对照),不需要 LLM 从自由文本里"发现"事实;②LLM 提取=每次编辑后一次网络调用+费用+延迟,违背无声助理;③确定性规则可解释、可断言、离线可用——与产品"本地优先"同构。LLM 唯一更擅长的是归纳高层结论("用户偏好活泼"),但这个可以延迟到注入时让生成模型自己消化原始统计,P2 再评估是否需要周期性离线归纳。

### D3 摘要注入:限长 + 优先级声明 + 观察不下结论

**为什么**:ChatGPT memory 的记忆污染是前车之鉴。三道防线:①≤200 字,不稀释核心 prompt 契约;②注入语固定带"与本次活动信息冲突时以活动信息为准"(表单永远赢,防档案过期事实压过本次输入);③facts 只收出现 ≥2 次的条目(单次观察 NOOP,防偶发污染);④摘要只陈述观察("近 5 次编辑段落平均变短 18%"),不发明结论("用户喜欢简洁"由生成模型自行消化)。

### D4 防漂移铁律(继承 prompt 契约)

档案只影响**风格与背景事实**,不改变「未给信息写待定、不编造」的既有契约——注入位置放在活动信息之后、以"仅供参考"定界,不进入 SYS_PLAN 规则本体。

### D5 时间衰减(Zep)

summarize 权重 ∝ count × 0.5^(age/180天)。组织会变:一年前的预算档位不该压过上个月的。不做双时间建模——衰减系数对单机单用户足够。

## 四、分期(与交接文档 A 节对齐)

- **P1 核心**(1 个新文件 profile.js + 5 处埋点小改 + ai.js 3 处拼接,~150 行):纯被动、零 UI、无新交互。
- **P2 显隐混合**:章节级 👍/👎(权重高于被动信号——IFllm 等研究的共识:显式信号贵但准,隐式免费但噪)。
- **P3 企业档案卡片**(设置页):查看/编辑/逐条删/一键清空 + 导出 JSON——ChatGPT saved memories 的本地版,隐私承诺("可审计可清除")的兑现。

## 五、验证设计(先测后写,延续修正轮方法)

| 层 | 断言 |
| --- | --- |
| update | 事件进→档案变;count/时间戳正确;≥2 次门槛;未知事件类型 NOOP |
| summarize | ≤200 字;含 count≥2 的事实;衰减生效(旧条目排序靠后);空档案返回 '' |
| 注入 | 有档案:prompt 含摘要+优先级声明;**无档案:prompt 与现状逐字节一致(零回归)** |
| E2E | 桩 AI 连续两次生成:第二次 prompt 可见第一次学到的公司名;清档案后第三次消失 |

## 六、风险与对策

| 风险 | 对策 |
| --- | --- |
| 记忆污染(错误偏好越积越偏) | ≥2 次入档;时间衰减;P3 一键清除;P2 显式否决一票降权 |
| 档案膨胀污染上下文 | 摘要硬限长;facts 每类只取 top3 |
| "懂你"变"吓你" | 全被动零弹窗;P3 人话呈现;只存本机写入产品文案 |
| localStorage 容量 | 档案 KB 级;events 环形缓冲封顶 500 条 |
| 隐私口径不一致 | 档案键随「清除配置」类操作一并提示;导出/删除入口与方案库同级 |

## 实现记录(P1,2026-09-30 当日完成)

**改动面**:新增 `app/assets/js/profile.js`(~210 行,纯函数 + localStorage);`ai.js` 拆出可测的 `formBrief`/`buildPlanMessages`/`buildRegenMessages` 并注入;5 个埋点各一行(`app.js` finishGen/saveDraftDebounced,`doceditor.js` saveNow/runAI/runSelOp);`index.html` 引入脚本。零 UI 改动、零新交互。

**与设计的两处偏差(工程化取舍)**:
1. 事件环形缓冲只存事件骨架(类型/话题/操作,不存 prev/new 全文)——全文本就在方案自身 `prev` 字段中,档案侧重复存储会放大 localStorage 压力;骨架已足够 P3 展示与算法升级。
2. `style.keptTerms`(保留的公司术语)未实现——确定性规则无法识别"术语"(需要分词),列入 P2 候选(用 👍/👎 显式信号或周期性离线归纳补)。

**实现中发现并修复的 bug**:条目归并的截断策略最初是"新词 unshift 挤掉老词",同批多套话删除时高频词会被挤掉、count 永远到不了 2;改为 push + 超限时按 count 优先保留,固定词表(套话)不截断。

**测试**:`test/run.js` 新增 [9] 段 11 断言(E1 计数/门槛、E2 统计与样本门槛、E3 热区、E4 选区、E5 去重、衰减、注入零回归、注入内容),先红后绿;全量 **40 通过 / 0 失败**;全模块语法检查通过。

**E2E(本地服务器 + 桩 fetch 捕获请求体)**:
- 第 1 场生成:prompt 无档案段(零回归),E1 落档 count=1
- 第 2 场生成:发出请求时 count 仍 1,门槛拦截,prompt 依旧无档案段
- 第 3 场生成:prompt 尾部出现「企业档案(仅供参考;与上述活动信息冲突时,一律以活动信息为准):常用组织:星海科技;面向人群:员工」,表单信息完整保留
- E2 编辑对照 ×3 → 摘要「用户倾向更简洁(编辑后内容平均缩短 81%);偏好以列表要点表达;避免「综上所述」类套话」
- `EP.profile.clear()` 后再生成:prompt 恢复至与无档案时完全一致的形态
