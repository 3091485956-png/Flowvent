# 17 · 记忆来源与运作机制 · 讨论稿(V1.2 方向)

> 2026-10-19 · 状态:**讨论中,未实施**。本文回答一个问题:记忆机制应该怎样运作。
> 前置:V1.1 已落地「捕获 → 编译 → 注入」(docs/16),本文补全剩余两环——**验证与修订**,并系统性回答"记忆从哪来"。

---

## 〇、产品视角一页纸(给决策者)

**是什么**:让产品从"通用模板工具"变成"越用越懂你的策划搭档"。类比带一个新策划专员:第一周写的东西处处是套路,三个月后张口就是"咱们公司致辞从不超过10分钟"。这个转变 = 记忆机制。它是一个学习循环:**看(观察你怎么用)→ 记(消化成清晰的了解)→ 用(下次写方案带上)→ 核实(看你有没有推翻)→ 改口(被推翻就忘掉)**。前三步已上线(记忆库图谱就是"记"的产物),本文讨论缺的后两步。

**记忆从哪来**(按可信度从高到低,类比助理听话的渠道):
1. 你亲口交代的——点"设为默认"、亲手改记忆 ✅已有
2. 你反复强调的——同一要求提3次,系统来问 ✅已有
3. 你改稿的方式——AI写完你怎么改,归纳出习惯 ✅已有
4. 你给的旧材料——导入的过往方案、笔记 ✅已有(但与前三类没分身价)
5. 你不说时的行为——**导出时哪些章节一字未改 = 用户用脚投的认可票** ❌完全缺失

**为什么**:
- 第二轮 50 份方案实测:记住偏好后,员工"想去指数"2.6 → 6.1 分;不记忆 = 每次从零交代
- 现在产品只学"你改了什么"(负信号),不学"你认可了什么"(正信号)——像只记得住批评、记不住点头的助理,会越学越束手束脚,记忆退化成"回避清单"

**为什么不**:
- 不做全息画像:记忆越膨胀越污染生成,也毁掉"一键清除"的承诺;小到 5 分钟能看完,才敢说数据你做主
- 不让记忆填内容:口碑底线是"没给的信息写待定,不编造";记忆管风格,不管事实
- 不记所有聊天:噪音远大于信号
- 不急着做多公司:没有真实场景就不付复杂度

**待拍板**:① 要不要补"认可"信号(第一优先建议做)② 记忆页显示"被采纳/被推翻"次数吗 ③ 笔记并进记忆吗 ④ 多公司记忆做吗(建议不做)

## 0. 核心命题

**记忆不是一个存储罐,而是一个循环:**

```
捕获 capture → 编译 compile → 注入 inject → 验证 verify → 修订 revise ─┐
      ↑──────────────────────────────────────────────────────────────┘
```

V1.1 打通了前三环;当前系统最大的缺口是**验证闭环**——记忆学到的内容,从来没有被用户的后续真实行为检验过。一个偏好被注入 100 次,系统不知道它对了 99 次还是 0 次。

---

## 1. 现状盘点(V1.1.1 基线)

| 环节 | 已有 | 缺口 |
| --- | --- | --- |
| 捕获 | 8 类事件:plan_generated / section_edited / section_ai_op / selection_op / form_defaults / past_plan_parsed / chat_message / preference_confirmed·rejected(+edit_induced) | **没有「接受」类事件**——只采集修改,不采集认可 |
| 编译 | AI 两步 CoT / 本地确定性兜底,水位线增量,tombstone 防复活 | 编译视野只有事件骨架(400 字截断 payload),**看不到方案定稿全文**;笔记库(ep_memory)不在编译源内 |
| 注入 | 两级(confirmed/inductive)+ 相关性排序 + 280 字预算 | 注入后无标记,效果不可追溯 |
| 验证 | — | **完全没有**。置信度来自计数,不来自结果 |
| 修订 | Review 队列 / lint(过时·孤页·重复)/ rawLog 环形缓冲 200 | 衰减只在旧 summarize 里,wiki 页面没有置信度衰减 |

## 2. 五个主张

### 主张一:来源按信任度分层,不同层走不同管线

不是所有记忆生而平等。按"离用户真实意图的距离"分五层:

| 层 | 来源 | 举例 | 处理方式 | 初始置信度 |
| --- | --- | --- | --- | --- |
| L1 显式 | 用户亲手操作 | 点「设为默认」、直接编辑记忆页面 | 直接入页,永不自动降级/删除 | 0.95 |
| L2 结构化行为 | 规则可判 | 确认闭环(重复 3 次)、表单默认值分布 | 确定性编译,无需 LLM | 0.7 |
| L3 编辑差异 | AI 初稿 vs 用户终稿 | section_edited 对、选区改写 | **必须 LLM 归纳**,单样本无意义,≥3 样本成页 | 0.6 |
| L4 导入文档 | 过往方案 .docx、MD 笔记 | intake 解析、笔记库 | 解析后标记为「历史证据」,可能过时,lint 重点盯 | 0.5 |
| L5 弱信号 | 环境行为 | 导出、复用、重开(主张二) | **只调置信度,不直接产生内容** | ±0.05/次 |

**现状问题**:L4 导入的偏好和 L1 确认的偏好只差一个 `level` 字段,`confidence` 不分来源一律 0.6/0.95——应让 confidence 从源头就反映信任层。

### 主张二:最强的信号还没被采集——「接受」

这是当前最大的盲区。系统只在用户**修改**时学习(编辑 diff、重写、撤销),用户**认可**时系统是瞎的:

- 用户导出 Word 时,哪些章节自 AI 生成后一字未改 = **最强的正信号**(section_kept)
- 生成后零编辑直接导出 = 整案接受(plan_exported 携带各章节编辑计数)
- copyPlan 复用旧方案 = 结构级认可

第二轮体验报告里"首段末尾补一句"能被归纳,靠的是编辑对;而"**框架完全不动**""直接照发"这类接受型习惯,现在根本采集不到。没有接受信号,记忆只学到了用户讨厌什么,没学到用户认可什么——模型的置信度会系统性偏向"用户总在不满"。

**埋点成本极低**:导出函数(app.js / doceditor.js 的 btn-word / btn-export / btn-edit-word)处统计各 section 的 `flags.ai` 是否仍在即可,零隐私新增(不离开本机)。

### 主张三:方案定稿全文应是编译的一等来源

现在编译只看事件骨架,AI 编译器不了解用户最终认可的方案长什么样。应新增:

```
plan_finalized { planId, sectionTitles, keptSections: 2~3 个代表章节全文(截断) }
```

触发时机:首次导出时(而不是每次保存——避免噪音)。AI 编译第二步(写入器)可引用代表样本,让页面 body 长出**具体事实**——"预算表按 8 科目拆分、合计必须精确到元",而不是抽象描述"用户偏好详细预算"。

### 主张四:笔记库必须并入编译源,否则「记忆库」名不副实

`ep_memory`(MD 笔记图谱)和 `ep_wiki`(编译页面)目前是两套并行事实、两个 UI 概念。笔记是用户**主动留下**的知识(公司制度、过往创意、品牌口径),信任度按主张一应为 L2 级——高于行为推断。

并入方式(零破坏):
- 笔记文件作为编译 source:`kind:'note'` 的引用页(只存标题+摘要,正文仍留 ep_memory),与实体页建 LINKS_TO
- AI 编译时可引用笔记内容做背景,但**笔记里的公司制度属"权威来源"**:与行为推断冲突时,笔记赢 → 产生 Review 而不是静默覆盖

### 主张五:验证闭环——注入效果必须回流

具体机制:

1. `assemble()` 注入时,被选中页面记 `lastInjectedAt`、`injectedCount++`(内存态随编译落库)
2. 后续 `section_edited` / `section_kept` 到达时,若该章节上下文曾注入页面 P:
   - 用户终稿**遵循** P(如确认偏好未被改写)→ `P.verified++`,confidence 微升(+0.02,上限 0.98)
   - 用户终稿**违背** P(确认级偏好被改写)→ 不是普通编辑:`P.violated++`,confidence 降 0.1;violated ≥ 2 → 自动生成 Review("记忆「X」连续被你的编辑推翻,是否已不再适用?")
3. confidence 是注入排序的一级因子,低于 0.35 的归纳级页面不再注入

这让 confidence 从"计数"变成"**被现实检验过的信念**"。也是 llm_wiki Review 机制的本意:防的不只是 AI 幻觉,还有记忆自身的过时。

## 3. 完整生命周期(目标态)

```
捕获  8+ 类事件(L1~L5 分层,含接受信号)          ← 埋点层,单一入口 record()
编译  水位线增量;AI 两步;视野含笔记与定稿样本     ← wiki.js,本地可兜底
注入  检索式(相关性×置信度×两级),280 字预算      ← ai.js memBlock
验证  injected 标记 → 后续行为回流 verified/violated ← 新增
修订  矛盾→Review;过时→lint;低信→停注入;删除→tombstone ← 已有,补衰减
```

## 4. 不变的边界(铁律,历次裁定汇总)

- 数据只存本机、可审计、可一键清除;记忆必须**小到人能看完**(rawLog 200 / pages 80 / 摘要 280 字)
- 记忆不填事实:未给信息写「待定」,表单信息 > 记忆,结构关键 prompt(polish)不吃结构向记忆
- venue/budget/department 只收集不注入;部门人名永不注入(I-5)
- 记忆只影响风格与背景,永不改变「不编造」契约

## 5. 遗留的结构性问题:多公司命名空间

所有记忆共享单一命名空间。用户若服务多家公司(甲方乙方、集团公司多品牌),A 公司的记忆会污染 B 公司的方案。页面模型下的自然解法:

- company 实体页升级为**命名空间锚点**:`plan_generated` 时记录 `companyKey`
- 注入时按当前表单的公司过滤(本公司页面优先,通用偏好页全公司共享)
- 即 docs/12 遗留的「facts 按公司分组」,在页面模型下不再需要迁移数据——只需编译时归类

## 6. 分期建议

| 期 | 内容 | 成本 | 价值 |
| --- | --- | --- | --- |
| P1 | 接受信号:plan_exported / section_kept 埋点 + confidence 回流(主张二 + 五) | 小:3 处导出埋点 + wiki 置信度规则 + 测试 | ★★★ 补上最大盲区 |
| P2 | 定稿样本入编译:plan_finalized + AI 写入器 prompt 带代表章节 | 中 | ★★ 页面长出具体事实 |
| P3 | 笔记库并入:ep_memory → note 引用页 + 权威级冲突裁决 | 中 | ★★ 概念统一 |
| P4 | 多公司命名空间 | 中 | 视用户是否多公司而定 |

## 7. 待用户决策的点

1. **P1 接受信号**:导出时埋点统计章节保留情况,是否同意?(唯一需要注意的:埋点只在本机,不涉新增隐私)
2. **置信度可见性**:页面详情是否展示"注入 N 次 · 被验证 M 次 · 被推翻 K 次"?(透明 vs 界面噪音的取舍)
3. **笔记库并入**(P3)是否提前?若常用 Obsidian/MD 工作流则价值高
4. **多公司**(P4):你是否实际服务多家公司?若否,P4 无限期推迟

## 附 · Claude Code 记忆机制源码对照(2026-10-19,借鉴结论)

> 依据用户提供的 Claude Code 源码(services/extractMemories、memdir/*、services/SessionMemory、services/compact/sessionMemoryCompact)。
> 以下为产品层借鉴结论,完整分析见对话记录。

**Claude 的核心设计**(源码印证):
1. 记忆=「给未来自己留的便签」:一话题一文件,frontmatter(name/description/type),MEMORY.md 仅作索引(一行一条,常驻)
2. 四类型:user(用户是谁)/ feedback(怎么配合干活)/ project(在做什么事,带 Why)/ reference(去哪找信息)
3. **feedback 明确要求"从失败 AND 成功双录":"只记纠正会越来越畏手畏脚"** —— 直接印证本文主张二(接受信号是最大盲区)
4. 检索两段式:索引常驻;小模型按 description 选 ≤5 条全文注入,"不确定就不选"(精确优先于召回)
5. **每条注入记忆带年龄与过时警告**:"47 days ago · point-in-time observation, not live state · verify before asserting"——引用越具体越权威,过时越危险
6. "为什么不记"负面清单:可从现状推导的不记、已文档化的不记、临时状态不记;**用户点名要存也先过滤**(存活动日志 → 反问"哪里出乎意料")
7. 记忆正文结构:规则 + **Why** + **How to apply**(知其所以然才能判断边界情况)
8. "忽略记忆"语义:当记忆库为空处理,不引用不对比不提及
9. 工程细节:游标增量(失败不推进)、主代理已写则跳过后台提取(互斥)、提取代理只能写记忆目录(权限笼)、失败静默重试

**秒策已殊途同归**:水位线增量+失败重试、编译互斥(确认事件直达)、一页一事、Obsidian 导出、280 字注入预算(比 Claude 的索引常驻更严)。
